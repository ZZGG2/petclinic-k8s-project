OVERVIEW

최종 아키텍처

요청 흐름: 사용자 → ALB → WEB(Nginx) → WAS(Tomcat) → DB

  • 네트워크 — VPC 1개, AZ 2개, Public / Private Node / Private DB 서브넷
  • 노드 — 시스템 컨트롤러는 ng-system, 앱은 Karpenter가 필요할 때 생성
  • 환경 — Kustomize dev(StatefulSet) / prod(RDS), WAS 설정은 동일
  • 확장 — WAS는 CPU(HPA), WEB은 요청 수(KEDA), 노드는 Pending 파드(Karpenter)

설계 원칙

  • 한 번에 하나씩 추가하고, 추가할 때마다 동작을 눈으로 확인
  • 설정은 이미지에 굽지 않고 런타임에 주입
  • 권한은 필요한 만큼만 (DB 계정 · IAM 모두)
STAGE 1

가장 단순한 3-Tier 개통

부가 기능 없이 ALB → WEB → WAS → DB가 연결되는 것만 먼저 성공시킴

구성

  • 콘솔로 VPC · 서브넷 6개 · IGW · NAT · Bastion, eksctl로 EKS 생성
  • WAS: Maven -P MySQL → Tomcat 11 멀티 스테이지 빌드
  • 외부 노출: Ingress 대신 Gateway API (GatewayClass → Gateway → HTTPRoute)
  • ALB 설정은 LoadBalancerConfiguration · TargetGroupConfiguration으로 분리
트러블슈팅 — 원인이 세 겹
  1. catalina.sh의 eval이 &, #을 셸 문법으로 해석 → JDK_JAVA_OPTIONS
  2. Running인데 404 → Secret + subPath로 설정 파일 주입
  3. Maven 필터링이 XML의 ${jdbc.url}까지 치환 → 빌드 후 플레이스홀더 복원
STAGE 2

DB 영속성 · 최소 권한 · 환경 분리

추가한 것

  • StatefulSet + EBS gp3 — 파드를 지워도 같은 이름, 같은 디스크로 복구 (WaitForFirstConsumer)
  • Seed Job — 스키마는 관리자 계정이 1회 적용, 앱 계정은 SELECT · INSERT · UPDATE · DELETE만
  • Kustomize — base + overlays/dev(StatefulSet) / overlays/prod(RDS)
  • ExternalName — 서비스 이름 petclinic-db는 그대로, 가리키는 대상만 RDS로
확인한 것 — DB 파드 삭제 후 데이터 유지 · 앱 계정 DROP TABLE 거부 · WAS 수정 없이 RDS 전환
STAGE 3

잘 버티는 파드 만들기

Probestartup · liveness는 DB를 거치지 않는 정적 경로, readiness는 매번 DB를 조회하는 /owners
/vets는 캐시 때문에 DB가 죽어도 200 → 사용 안 함
자원requests · limits + JVM MaxRAMPercentage=75, LimitRange · ResourceQuota
가용성replicas 2 · AZ/노드 분산 · maxUnavailable 0 · PDB minAvailable 1
로그네이티브 Sidecar (initContainers + restartPolicy: Always) + emptyDir
배치CronJob 5분 주기 DB 리포트 (Forbid, 실행 마감 시간)
확인한 것 — DB를 끄면 WAS는 트래픽에서 빠지지만 재시작 0회 · drain 중에도 200 유지 · PDB가 마지막 1개를 지킴
STAGE 4

오토스케일링 3단계

WAS · HPACPU 사용률 50% (requests 기준) · 2~4개 · 축소는 60초 안정화
WEB · KEDACloudWatch ALB RequestCount (파드당 분당 60건) + 평일 09~18시 최소 3개
노드 · KarpenterPending 파드 → 가장 저렴한 인스턴스 생성 (Spot 우선) · Consolidation · 한 번에 1대씩 정리

함께 한 설정

  • ng-system에 Taint → 시스템 컨트롤러와 앱 노드 분리
  • 파드 수의 주인은 하나 → Deployment에서 replicas 제거
  • KEDA 권한은 EKS Pod Identity + CloudWatch 읽기 3개 동작만
관찰 — HPA는 수십 초, KEDA는 CloudWatch 지연으로 2~3분 → 예측 가능한 트래픽은 cron으로 미리 확장
STAGE 5 · 시연

통합 시나리오

1연쇄 확장 — ALB 부하 → KEDA가 WEB 확장 → 자리 부족 → Karpenter 노드 추가 → 종료 후 Consolidation
2StatefulSet 복구 — DB 파드 삭제 → 같은 PVC · 같은 AZ 노드로 복구
3롤링 업데이트 / 롤백 — WEB v1 → v2 (상단 배지 색이 바뀜) → 롤백
4노드 점검 — kubectl drain 중 PDB로 서비스 유지
시연 팁 — 화면 상단의 WEB · WAS·DB 상태 점이 실시간으로 바뀝니다
